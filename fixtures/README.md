# Portable SDK conformance cases

`sdk-conformance.json` is language-neutral input/output evidence for SDK and
future native engine implementations. Each case has an operation, input,
expected public fields, source URL or repository document, and a rationale.
The `expected` object is a recursive subset assertion; implementations may add
provenance or result fields without breaking these cases. Primitive/null results
are compared exactly. Arrays are compared in full and in order.

Expected values were specified from published examples, independently checked
table cells, arithmetic, and the documented validation contract. They are not
snapshots generated by calling the SDK. Changes to expected numerical values
need source evidence. Changes to the fixture structure need a schema version.

Times use clock strings at the input boundary. Stable whole-hundredth and whole-
point assertions allow the same cases to be used from Swift, Kotlin, Rust, and
JavaScript. Non-JSON values such as `NaN` and `undefined` are tested separately
in JavaScript. Broader dataset and milestone boundary tests supplement these
small portable cases.

`empirical-parity.json` is different on purpose. It holds exact-hundredth
Turnmark Equivalence (`turnmark-empirical-2026`) conversions for every cell of `data/empirical.json`, computed
by the Python reference implementation in
`research/conversion-model/evaluate_and_train.py` (`engine_empirical_cs`) and
rewritten by every `--export-empirical-json` run. It is evidence that the Rust
engine applies the exported cells with the same arithmetic the model was
evaluated with, not a source-backed expectation; `cellsSha256` ties it to one
snapshot, and the Rust conformance test fails if the two disagree.
